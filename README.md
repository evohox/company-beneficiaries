# Конечные бенефициары компании

CLI на Python, который читает сущности и связи владения из CSV и рассчитывает эффективные доли физических лиц в выбранной компании. Учитываются прямое владение, несколько путей владения, самовладение и взаимное владение при допустимой системе уравнений.

## Установка и запуск

Проверено на Windows 11 x64 с Python 3.12.3. Основные зависимости: NumPy 2.5.3, SciPy 1.18.1 и pytest 9.1.1. Версии зависимостей закреплены в `requirements.txt`.

Из корня репозитория в PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe solve.py --entities entities.csv --edges edges.csv --target C900003 --threshold 0.0001
```

В Linux/macOS окружение можно создать командой `python3.12 -m venv .venv`, затем использовать `.venv/bin/python` вместо `.\.venv\Scripts\python.exe`.

Аргумент | Значение |
|---|---|
| `--entities` | Обязательный путь к CSV с колонками `id,type,name` |
| `--edges` | Обязательный путь к CSV с колонками `owner_id,owned_id,share` |
| `--target` | Обязательный идентификатор целевой компании |
| `--threshold` | Конечное неотрицательное число; по умолчанию 0.0001

Доли задаются числами: `0.25` означает `25%`. Результаты со строго меньшей долей, чем порог, исключаются. Равенство порогу сохраняет результат. При нулевом пороге выводятся только физлица с положительной эффективной долей.

Результат записывается в stdout как CSV в UTF-8:

```csv
person_id,name,effective_share
P900001,Ромбов Иван Иванович,0.75
P005524,Морозов Елена Николаевич,0.25
```


Сортировка - по убыванию доли, при равных долях - по ID. Порог применяется до форматирования; числа выводятся с точностью до 12 значащих цифр. Запятые и кавычки в именах обрабатывает `csv.writer`. Если подходящих бенефициаров нет, выводится только заголовок.

Диагностика и статистика загрузки отправляются в stderr. Код завершения: `0` - успех, `1` - обработанная ошибка загрузки или расчёта, `2` - ошибка аргументов командной строки.

## Алгоритм

1. Сущности загружаются в словарь по ID, связи - в список рёбер.
2. Строится индекс входящих связей: для каждой компании хранится список её владельцев и их долей.
3. От целевой компании выполняется обход вверх по компаниям-владельцам. Физлица завершают ветви. Используются стек и множество посещённых компаний, поэтому обход не зависит от ограничения глубины рекурсии.
4. В выбранном подграфе удаляются одинаковые связи и проверяются противоречия между долями одной пары владелец–компания.
5. Для компаний подграфа строится разреженная матрица прямого владения и решается одна линейная система.
6. Вклады прямых владений каждого физлица умножаются на рассчитанные коэффициенты компаний и суммируются. После этого применяются порог и сортировка.

### Формула расчёта

В матрице `W` строка - компания-владелец, столбец - компания, которой она владеет. Физлица в матрицу не входят.

Для выбранной цели решаю систему:

```text
(I - W)w = e_target
```

`I` - единичная матрица, `e_target` - вектор с единицей на позиции цели. Вектор `w` содержит коэффициенты, с которыми владение каждой компанией влияет на результат. Доля человека получается так:

```text
eff(P, target) = Σ direct(P, C) × w[C]
```

В коде это `weights` и сумма вкладов через `math.fsum`. Матрица хранится в CSC, систему решает `scipy.sparse.linalg.spsolve`. Одного решения хватает для расчёта всех физлиц.

### Почему так

Система уравнений позволяет учитывать циклы. При переборе путей пришлось бы учитывать повторные проходы, а простое отсечение посещённых вершин теряло бы часть вкладов. Расчёт по топологическому порядку подходит только для графа без циклов. Итерационный расчёт требует критерия остановки и может медленно сходиться.

Разреженная матрица экономит память на нулях. Перед её построением выбираю только компании, связанные с целью.

## Обработка данных

- Читается UTF-8 с BOM и без него, убираются пробелы по краям полей, чтобы один ID с разными отступами не считался разными сущностями. Порядок колонок может отличаться, их состав и количество должны совпадать. Содержание имён не исправляется.
- Ошибки заголовка, синтаксиса CSV и записей сущностей останавливают запуск, чтобы не строить граф по неоднозначным ID и неправильно разобранным данным. У сущности должны быть ID, непустое имя и тип `person` или `company`. Повторные ID запрещены, чтобы записи не перезаписывались. Цель должна быть существующей компанией.
- В CLI пропускаются с предупреждением связи с неверным числом полей, неизвестным ID, физлицом в качестве объекта владения или недопустимой долей, чтобы отдельная ошибочная запись не останавливала весь расчёт; предупреждение позволяет увидеть, что исключено. Доля должна быть конечным числом в диапазоне `[0, 1]`.
- Нулевые доли пропускаются: они не дают вклада. Самовладение и взаимное владение сохраняются. Они допускаются заданием и влияют на эффективные доли.
- Одинаковые положительные связи в выбранном подграфе учитываются один раз. Считаем их повтором одного факта владения, иначе доля будет учтена несколько раз. Если у одной пары разные доли, расчёт останавливается: оснований выбрать одну из них нет. Сравниваются загруженные `float` без допуска. Конфликты вне подграфа не проверяются, т.к. эти связи не участвуют в расчёте выбранной цели.
- Доли не нормализуются: это изменило бы исходные значения без основания. Неизвестные владельцы не добавляются. Компания без владельцев остаётся в графе; если расчёт успешен и вкладов физлиц нет, выводится только заголовок.

Во входе 52 011 сущностей и 88 863 записи связей. Загрузчик пропускает 1 394 доли больше 1 и 150 нулевых долей. Остаётся 87 319 связей до удаления повторов в подграфе.

У `C025145` сумма прямых долей после очистки равна 1.1637. В компаниях выше по графу тоже есть суммы больше 1. Поэтому сумма выведенных эффективных долей получилась около 1.24797. Такие несогласованности текущий код автоматически не исправляет.

### Ограничения расчёта

При вырожденной системе расчёт останавливается, поскольку однозначно определить коэффициенты нельзя. Вырожденная система вызывает ошибку,  в том числе замкнутый 100%-й цикл без физлиц. После решения проверяется конечность и неотрицательность коэффициентов, затем они подставляются в исходную систему. 

Сумма всех путей сходится при `ρ(W) < 1`. Спектральный радиус и обусловленность отдельно не вычисляю. Поэтому проверка невязки не даёт полной гарантии точности для плохо обусловленных систем.

## Сложность

`N` - число всех сущностей, `M` - число входных записей связей, `k` - число компаний выбранного подграфа, `b` - число результатов после отсечки.

Чтение файлов и полный индекс входящих связей требуют `O(N + M)` времени и памяти. Обход и сбор вкладов линейны по размеру подграфа. Сортировка ID компаний занимает `O(k log k)`, сортировка результата - `O(b log b)`.

Стоимость решения зависит от структуры матрицы: при факторизации могут появляться новые ненулевые элементы. Верхняя оценка для этого этапа - `O(k³)` времени и `O(k²)` памяти.

Итого: `O(N + M + k³ + b log b)` времени и `O(N + M + k²)` памяти. Подготовка CSC-матрицы также укладывается в эту оценку. Предполагаются ограниченный размер CSV-записей, арифметика фиксированной точности и средняя амортизированная стоимость операций со словарями и множествами.

## Проверка корректности

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

44 теста проверяют загрузку, обход, повторы связей, расчёт долей и запуск CLI. Среди случаев есть циклы, цепочка из 2000 компаний, вырожденная система, посторонние связи, кавычки в CSV и доли на границе порога.

Малые контрольные примеры проверяются вручную:

- `C900003`: два пути дают `1 × 0.4 + 1 × 0.35 = 0.75`.
- `C900012`: из `f_A = 0.5 + 0.5f_T` и `f_T = 0.5 + 0.5f_A` получается `f_T = 1`.
- `C91001999`: все доли цепочки равны 1, их произведение тоже равно 1.
- `C900022`: самовладение даёт `f_A = 0.6 / (1 - 0.1)`. Вклад в цель - `f_A × 0.8 = 8/15`.

Для `C025145` отдельного эталона всех долей нет. Сохранённый CSV показывает результат прогона, но сам по себе не доказывает его правильность.

## Если данных станет в 100 раз больше

Это примерно 5.2 млн сущностей и 8.9 млн связей. Основные ограничения - хранение всего графа в объектах Python и повторное чтение файлов для каждой цели. Большие циклические подграфы могут также сделать решение системы дорогим.

Сначала измерил бы время по этапам и пиковую память. Дальше рассмотрел бы:

- числовые индексы и компактные массивы для связей; если памяти не хватит - индекс по `owned_id` в БД;
- одну загрузку данных для нескольких целей и повторное использование факторизации при совпадении матриц;
- выделение компонентов сильной связности: ациклические участки считать по порядку, системы решать внутри циклических компонентов.


## Ответы на вопросы задания

### Какие решения не были заданы условием

Некорректные записи связей решил пропускать с предупреждением, а при ошибках в сущностях - останавливать программу.

В выбранном подграфе одинаковые связи учитываются один раз. Если для одной пары указаны разные доли, выдаётся ошибка: выбрать правильную по этим данным невозможно. По той же причине не нормализую суммы долей.

Для расчёта выделяю подграф нужной компании и решаю одну систему уравнений. Полученные коэффициенты использую для всех физлиц.

### Как проверялось, что ответ правильный

Использованы примеры с заранее вычисляемым ответом, тесты ключевых ошибок и полного запуска, ручной разбор четырёх контрольных случаев, проверка невязки и сохранённые результаты прогонов. Проверялись также формат CSV, имена из исходного файла, состав физлиц, порядок и порог. Ограничения проверки сложных и плохо обусловленных случаев обозначены явно.

### Что сделать в первую очередь при наличии ещё трёх дней

1. Расширить проверку математической части: небольшие случайные графы со сходящейся системой, независимый эталон на точных дробях и случаи, близкие к вырождению. Приоритет - выявить ошибки, которые не проявляются на нескольких контрольных примерах.
2. Добавить отчёт о качестве данных: суммы прямых долей, повторы, конфликты, причины пропуска и их влияние на выбранную цель. Это позволит объяснять результаты выше или ниже ожидаемой суммы без изменения исходных долей.
3. Измерить память и время по этапам на увеличенных данных. По результатам выбрать между компактным хранением графа, обработкой нескольких целей за одну загрузку и расчётом по компонентам сильной связности.
